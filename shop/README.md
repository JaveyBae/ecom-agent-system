# ShopSim 模拟商城的业务后端

商品、用户、订单、物流和售后都存在一个 SQLite 数据库里（`shop/shop.db`），代码在 `src/ecom_agent_system/shop/`。

- **商品**：ShopSimulator 的 23,421 件商品，带三级类目、规格和价格
- **用户**：ShopSimulator 购物任务里的用户画像，按内容去重后 4,666 个，带会员等级和省市区
- **订单、物流、售后**：由带随机种子的模拟器生成，同一个种子每次结果完全一样
- **规则**：发货时效、送达时效、退货期限、运费、补偿金额都读 `knowledge/platform_rules.yaml`，和知识库检索到的规则文本是同一份

## 生成数据库

```bash
uv run ecom-shop build --products <ShopSimulator 的 fine_items_eval_train_all.json.gz>
# 也可以设置环境变量 SHOPSIM_PRODUCTS；--orders、--days、--seed、--now 可调
```

默认生成 3,000 个订单，分布在 2026-10-24 12:00（模拟世界的“当前时间”）之前的 60 天里，几秒钟就能生成完。

评测用的世界单独生成，换一个种子、订单多一些，稀有的物流情形（破损拒收、物流停滞、大额丢件）才够挑出每种 8 个场景：

```bash
uv run ecom-shop --db shop/eval.db build --products <同上> --orders 10000 --seed 7
```

`shop/shop.db` 留给控制台演示和以后的训练，`shop/eval.db` 只用来生成评测套件（见根目录 README 的“评测”）。两个库订单不重合，顾客是同一批画像。

商品数据不随仓库提交，生成的数据库也不提交。ShopSimulator 的上游仓库是 [ShopAgent-Team/ShopSimulator](https://github.com/ShopAgent-Team/ShopSimulator)，本地副本里没有找到许可证文件，公开仓库前要先确认数据的使用条款。

## 查看数据

```bash
uv run ecom-shop stats                      # 订单、物流情形、售后的分布
uv run ecom-shop orders U000123             # 某个用户的订单
uv run ecom-shop order SO261013002432       # 订单详情
uv run ecom-shop track SO261013002458       # 物流轨迹和异常提示
uv run ecom-shop check SO261013002432 退货退款 七天无理由 --opened
uv run ecom-shop ticket AS00000477          # 售后进度
uv run ecom-shop track SO261013002458 --now "2026-10-30 12:00"   # 换一个时刻看
uv run ecom-shop ticket AS00000477 --now +5d                       # 也可以写相对当前时间的偏移：+5d、+12h、-2d
```

输出是 JSON，和以后 agent 工具的返回值一致。

## 时间模型

所有操作都显式传入“当前时间”。物流轨迹在商家发货时就整条生成，售后进度在动作发生时排好（商家什么时候同意、退货哪天到仓、哪天退款），包括未来的时间点；查询只返回不晚于当前时间的部分。这样：

- 同一份数据可以在任意时刻查看，把时间往后拨就能看到退款到账
- 数据库里存着完整的未来，任务生成器和评测可以直接拿来当标准答案
- 买家撤销售后时，删掉还没发生的事件

## 物流模拟

简化：所有商品从杭州仓发货，退货寄回杭州仓，所以“同城”指杭州。收货区域按 P-SHIP-08 分为同城、江浙沪、一般、偏远（新疆、西藏、青海、宁夏、甘肃、内蒙古）；用户画像里偏远地区的人很少，生成订单时按区域加权抽样。

每张发货单有一个情形，决定轨迹怎么走：

| 情形 | 概率 | 3,000 单里 | 对应规则 |
|---|---|---|---|
| 正常 | 71% | 2,096 | 按区域时效送达 |
| 运输延误 | 8% | 274 | 超过承诺送达日期（P-SHIP-08） |
| 延迟发货 | 6% | 182 | 超过 48 小时才发货（P-SHIP-01、02） |
| 未经同意放快递柜 / 驿站 | 3% / 2% | 92 / 59 | P-SHIP-09 |
| 物流停滞 | 3% | 89 | 中途超过 7 日（偏远 12 日）不更新，之后恢复（P-SHIP-07） |
| 虚假发货 | 2% | 57 | 填单号后超过 24 小时才揽收（P-SHIP-03） |
| 丢件 | 2% | 60 | 停滞后不再更新 |
| 代签 | 2% | 59 | P-SHIP-09 |
| 破损拒收 | 1% | 32 | P-SHIP-10 |

情形存在 `shipments.scenario` 里，相当于标准答案，查询接口不返回。查询返回的是轨迹和根据规则算出的提示，例如“物流信息已 8 天未更新，视为物流异常，可以申请补发或全额退款（P-SHIP-07、P-SHIP-06）”。

## 政策引擎

`policy.py` 只做判断，不读写数据库，每个结论都带依据的规则编号：

| 判断 | 规则 |
|---|---|
| 七天无理由退货的期限：普通、黄金 7 日，铂金 15 日，钻石 30 日，自签收次日起算 | P-RET-01、P-MEM-01 |
| 品类例外：定作、鲜活易腐法定不适用；已拆封的数字化商品不适用；食品、化妆品等只有商品页标注且下单时确认了才不适用；激活类电子产品激活后才不适用 | P-RET-02、P-CAT-01～03 |
| 拆封查验不影响退货 | P-RET-03 |
| 退货运费：运费险赔付，黄金及以上会员免运费，否则 10 元、偏远 25 元 | P-RET-05、P-MEM-01 |
| 极速退款：铂金、钻石会员填写退货单号后平台先行退款 | P-MEM-01 |
| 质量问题：签收 7 日内可退可换，15 日内可换，之后只能维修，运费商家出；耐用商品 6 个月内商家举证 | P-QA-01、P-QA-02 |
| 仅退款只用于物流异常、破损拒收和生鲜 24 小时内变质 | P-SVC-05、P-SHIP-06/07/10、P-CAT-02 |
| 发货时间的认定、延迟发货补偿（实付 5%，5～30 元）、超时 72 小时可取消 | P-SHIP-01～04 |
| 已发货、未签收的可以拦截：顾客原因的往返运费按两程退货运费从退款里扣；商家延迟发货的由商家承担 | P-SHIP-05 |
| 商家填单号之前可以改详细地址（同一区县），之后只能拦截 | P-SHIP-11 |
| 质量问题、运输损毁、生鲜变质要说出具体问题，只说“质量不好”不受理 | P-QA-05 |
| 智能客服的办理权限：不退货的退款和补偿，50 元以内直接办，50～1000 元提交后先人工审核，超过 1000 元不能办、要转人工 | P-SVC-04 |

商品属于哪种情况由 `category_policy.yaml` 按类目前缀决定，商家是否标注“不支持七天无理由退货”按 60% 的比例随机生成（`mark_rate`）。

## 售后流程

| 类型 | 状态 |
|---|---|
| 退货退款 | 待商家处理 → 待买家退货 → 买家已退货 → 商家已收货 → 退款成功；铂金、钻石会员的七天无理由退货在寄回后直接退款成功 |
| 换货 | 待商家处理 → 待买家退货 → 买家已退货 → 商家已收货 → 换货已发出 → 已完成 |
| 仅退款 | 待商家处理 → 退款成功 |
| 延迟发货补偿 | 平台处理中 → 补偿已到账 |
| 拦截退款 | 拦截中 → 已拦截，退回中 → 商家已收到退回商品 → 退款成功；拦截生效前已经签收的是拦截失败 |

几条分支：

- **商家拒绝**：退货、换货申请有一定概率被商家拒绝（七天无理由未拆封 6%、已拆封 40%，质量问题 25%），之后顾客可以申请平台介入（P-SVC-06、P-SVC-03）。平台在 3 个工作日内判定，七天无理由的拒绝 90% 不成立、质量争议 70% 不成立，不成立的回到“待买家退货”，成立的“已关闭”。
- **人工审核**：智能客服提交的仅退款超过 50 元时，先进入“待人工审核”，1～8 小时后“人工审核通过”，再交给商家处理（P-SVC-04）。
- **拦截**：拦截在 2～12 小时后生效，生效前已经签收的拦截失败；成功的删掉原来还没发生的派送事件，换成“拦截退回”“退回商家”。

商家在 48 小时处理时限内的随机时刻答复，超时由系统自动同意（P-RET-06）；收到退货后 3 日内退款，约 10% 的商家逾期，由平台自动退款（P-RET-07）。

生成数据时，顾客会按订单的物流情形办理售后：延迟发货的申请补偿或取消订单，物流异常和破损拒收的申请仅退款，已签收的约 20% 申请退货或换货；被商家拒绝的，75% 会申请平台介入。顾客的动作走和 agent 相同的接口，不符合条件的会被拒绝（例如标注了不支持七天无理由的食品）。当前时间下 694 个售后单的状态：退款成功 357、补偿已到账 128、待买家退货 56、已完成 43、已撤销 29、买家已退货 28、商家拒绝 16、已关闭 11、待商家处理 11、商家已收货 10、换货已发出 3、平台介入中 2。

## 接口

`service.Shop` 的方法就是以后 agent 的工具，都返回能直接转成 JSON 的 dict，不允许的操作抛出 `ShopError`（消息可以直接给用户看，附带政策引擎的判断）：

| 方法 | 用途 |
|---|---|
| `find_user(phone=, email=)` | 按注册手机号或邮箱核实身份（P-SVC-01） |
| `list_orders` / `get_order` / `track_shipment` | 查订单和物流 |
| `check_after_sales` | 只判断能不能办、怎么办，不创建售后单 |
| `create_after_sales` / `submit_return_shipment` / `cancel_after_sales` / `get_after_sales` | 办理售后、寄回商品、撤销、查进度 |
| `cancel_order` | 发货前取消订单，超时未发货的同时发放补偿 |
| `check_change_address` / `change_address` | 发货前改详细地址；修改按时间记录，查更早的时刻还是旧地址 |
| `urge` | 催发货、催派送：开一张工单，商家或物流公司过几个小时答复原本排好的发货、送达时间；24 小时内重复催不重复通知 |
| `request_intervention` | 商家拒绝后申请平台介入 |
| `hand_off` / `list_work_orders` / `get_work_order` | 转人工客服（开工单，几分钟内人工接入）、查工单 |
| `place_order` | 下单，检查规格、按规格算价格（生成模拟订单用） |
| `import_order` | 记下店铺前台已经成交的一单，规格和成交价照前台的记录存（购物 agent 的购买用，见下一节） |

## 工单、审计和对话记录

接入售后 agent 以后加的几张表（旧库打开时自动补上）：

| 表 | 内容 |
|---|---|
| `work_orders`、`work_order_events` | 转人工、催发货、催派送的工单和进度，和售后单一样按时间生效 |
| `order_changes` | 订单信息的修改（目前只有收货地址） |
| `audit_log` | 售后 agent 的每次办理和每次被拦下的调用：模拟时间、真实时间、会话、顾客、工具、参数、结果（已执行、顾客未确认、政策不允许、凭证不足、需转人工、越权、重复请求等） |
| `conversations` | 每段售后对话的摘要和办成的事，同一位顾客下次来时放进 agent 的上下文 |
| `customer_notes` | 顾客交代的、关于自己的事（收货习惯、退款方式），agent 用 `remember_note` 记下，带时间和会话，下次放进档案 |

## 接入购物 agent

[shopping-grpo-longhorizon](https://github.com/JaveyBae/shopping-grpo-longhorizon) 的购物 agent 在 ShopSimulator 里搜索、比较、选规格、下单。这边接在它下单之后：agent 买下的商品记成订单，接着走发货、物流和售后。agent 和 ShopSimulator 的代码都不用改。

```text
购物 agent（评测 / 采集）──HTTP──▶ 订单网关 :5701 ──原样转发──▶ ShopSimulator :5700
                                      │ 点 Buy Now 时
                                      ▼
                       orders / order_items / agent_purchases → 物流 → 售后
```

有两种接法，代码在 `purchases.py` 和 `gateway.py`：

```bash
# 1. 实时：在 ShopSimulator 前面起网关，把评测的 SHOPSIM_BASE_URL 指过来
uv run ecom-shop gateway --label grpo-step100          # 监听 5701，转发到 5700（--upstream 可改）
SHOPSIM_BASE_URL=http://127.0.0.1:5701 bash scripts/evaluate.sh grpo   # 在 shopping-grpo 仓库里运行

# 2. 离线：把已有评测轨迹里的购买补记成过去 20 天的订单，并模拟顾客收货以后的动作
uv run ecom-shop import-trajectories outputs/evaluation/grpo/trajectories.jsonl --label grpo-step100

# 按购物 agent 汇总：买得对不对、成交额、退货、退款
uv run ecom-shop agent-orders
```

网关的请求和响应都原样转发，只在 interact 以购买结束时记一单，订单号放在响应头 `X-Shop-Order-Id` 里。订单写不进库时只记日志，不影响评测。网关的时钟从库里的当前时间开始，跟着真实时间走，每记一单就把库里的当前时间推到这一刻，所以新订单刚下单、还没发货，要用 `--now +3d` 往后看。离线导入的订单分布在当前时间之前的 `--days` 天里，导入时模拟顾客收货后的动作，到当前时间为止，重复导入会跳过已导入的轨迹。

几处对接细节：

- **谁买的**：用购买结果里 `goal.user_persona` 找库里的用户，不用 reset 返回的画像。任务没有画像时，ShopSimulator 会沿用这个环境槽位上一个任务的画像。只有 4,666 / 23,421 个任务带画像（Final-200 评测集里是 38 / 200），没有画像的任务按任务编号固定分给一个用户，`agent_purchases.persona_matched` 记为 0。
- **规格**：ShopSimulator 把规格名和选项转成了小写，而且只选一部分规格也能下单。入库时不区分大小写对回原写法（`#p01` → `#P01`），只有一个选项的规格自动带上，没选的不记。
- **价格**：用 ShopSimulator 按所选规格算出的成交价，不重新计算。
- **任务编号**：每件商品正好对应一个任务，任务编号就是商品在数据里的下标。网关从 reset 请求里记下每个槽位的任务；中途才接上网关的，从会话名 `slot-3-8187` 里取。

`agent_purchases` 表把订单和购物 agent 的一次任务连起来：标签、任务编号、轨迹 ID、Reward v3 的购买结果（`gold_purchase` / `valid_alternative_purchase` / `partial_alternative_purchase` / `wrong_purchase`）、没通过的硬约束、用户需求原文。

离线导入时，顾客收货后申请七天无理由退货的概率按购买结果区分。这是模拟用的假设，不是统计出来的数，在 `purchases.NO_REASON_RETURN_RATE` 里调：

| 购买结果 | 七天无理由退货概率 |
|---|---:|
| `gold_purchase`（买中目标商品） | 12%（和模拟订单一样） |
| `valid_alternative_purchase`（可接受的替代品） | 20% |
| `partial_alternative_purchase`（部分满足） | 45% |
| `wrong_purchase`（硬约束没满足） | 80% |

退货申请照样过政策引擎，买错了也不一定退得了。例如部分满足的粉底液属于化妆品，商品页标注了不支持七天无理由退货，申请会被 P-RET-02 拒绝，这类在 `agent-orders` 的 `rejected_requests` 里单独统计。

已经验证过的：用 shopping-grpo 自己的评测循环（`collect_tasks`），模型换成写死的脚本策略（搜索、打开第一个结果、选第一个规格、购买），在真的 ShopSimulator 上跑了 Final-200 里的 10 个任务，经过网关全部记成订单：4 个带画像的任务对上了用户，规格大小写都对回了原写法；同一批轨迹离线导入，重复导入全部跳过。脚本策略只用来验证链路，不代表模型能力。

注意：

- veRL 训练的 rollout 走同一个接口，训练时不要接网关，否则每条 rollout 的购买都会记成订单。
- 同一次评测不要既接网关又离线导入，会记两遍（网关拿不到客户端生成的轨迹 ID，没法去重）。

## 还没有做的

- 价格保护、优惠分摊、优惠券和积分退还（P-PRICE-01～03）：订单里还没有优惠和价格变动
- 维修、签收核实（P-SHIP-09）、赠品（P-RET-04）、预售定金（P-CAT-04）
- 改地址只能改同一区县内的详细地址，不检查新地址是否真实
- 人工审核、人工客服、平台判定都是按概率排好的结果，没有真的“人”在处理
- 一个订单只有一种商品（可以买多件）
- 网关实时记下的订单不模拟顾客收货以后的动作；这些订单的售后由 `ecom-agent scenarios` 生成场景、售后 agent 处理（见根目录 README）
- 还没有用真实模型（Base / SFT / GRPO）的评测轨迹跑过导入：轨迹在 shopping-grpo 的 `outputs/` 里，不在 GitHub 上
