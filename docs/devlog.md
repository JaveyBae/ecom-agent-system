## 1. 法规知识库

售后 agent 要能说出依据，所以先做知识库。27 部现行有效的法律、行政法规、司法解释、部门规章和规范性文件按“条”切分，2,550 条；平台规则是虚构平台“ShopSim 模拟商城”的 40 条，参照行业做法自拟，每条标注依据的法规条文，由模板和参数渲染，参数同时给政策引擎和场景生成用，三处不会不一致。真实平台的规则受著作权保护、协议也禁止抓取，没有抓。

检索是 BM25 + Qwen3-Embedding-0.6B，加权 RRF 融合；顾客说“七天”“快递柜”“假货”，法条写“七日”“智能快件箱”“假冒”，所以 BM25 的查询按 121 条同义词表扩展，扩展词降权到 0.3。冒烟评测（17 条法规问题、12 条平台规则问题）上混合检索 R@1 0.53、R@5 0.76；最高法 19 个典型案例只用基本案情作查询，命中@10 只有 0.42，长尾条文找得到法规找不准条文。结论是 agent 该先把顾客的话改写成法律问题再检索，并且分层检索：先查平台规则，再沿 `legal_basis` 取法条。43 道检索决策题（该不该检索、检索词写得好不好）留给接上模型以后评。细节和全部表格在 [knowledge/README.md](../knowledge/README.md)。

## 2. 模拟商城

一个 SQLite 库放商品（ShopSimulator 的 23,421 件）、用户画像（4,666 个）、订单、物流和售后。两个设计决定：

- **时间显式传入**。物流轨迹在发货时整条生成，售后进度在动作发生时排好，包括未来的时间点；查询只返回不晚于“当前时间”的部分。同一份数据可以在任意时刻查看，把时间往后拨就能看到退款到账；库里存着完整的未来，评测可以直接拿它当标准答案。
- **政策引擎只做判断，不读写库**，每个结论带规则编号：七天无理由的期限和品类例外、退货运费、质量问题的处理、仅退款的适用情形、延迟发货的认定和补偿、拦截、改地址、凭证要求、智能客服的办理权限。

9 种物流情形（正常、运输延误、延迟发货、放快递柜、物流停滞、虚假发货、丢件、代签、破损拒收）按概率分配，情形本身是标准答案，查询接口不返回。商家拒绝、平台介入、人工审核、拦截生效与否都是按概率排好的结果。订单网关在 ShopSimulator 前面原样转发，购物 agent 点 Buy Now 时记一单，验证过用脚本策略跑 Final-200 里 10 个任务全部记成订单。细节在 [shop/README.md](../shop/README.md)。

## 3. 文件桥和第一次整条链路（10-24）

模型后端除了 OpenAI 兼容接口和本机 transformers，还做了一个文件桥：每一轮把请求写进目录，等外部写回决策，Claude Code 或人都可以扮演模型。10-24 用它走通了整条链路：Final-200 里随机抽 3 个任务购物（都是 `gold_purchase`，经网关记成 3 个订单），再从这些订单生成 3 个售后场景（两个延迟发货补偿，其中一个虚假发货；一个七天无理由退货并追问运费的法律规定），3 段都过了当时的检查，追问时检索并引用了《消费者权益保护法》第二十五条和《网络购买商品七日无理由退货暂行办法》第十八条。样本只有 3 个，只说明链路能跑通；那时的评分只有两条硬性要求。

## 4. 售后 agent 和 harness

模型只决定调哪个工具、填什么参数、怎么回复；能不能办、办多少钱由 harness 和政策引擎决定。15 个工具：查订单和物流、售后判断、提交和撤销售后、取消订单、改地址、催单、申请平台介入、查工单、记备注、检索法规、转人工。办理类工具依次过：参数检查、身份隔离、政策判断、凭证、办理权限和风控、确认卡片，然后在保存点里执行，同一段对话里重复的请求返回第一次的结果，每次办理和每次被拦下的调用进审计日志。

几个具体的取舍：

- **别人的订单一律“不存在”**，不透露是否存在，记为越权；只读调用被拦不算 agent 的失败（查之前没法知道是不是别人的单），办理类被拦才算。
- **办理权限连同判断一起给模型**。`check_after_sales` 返回 `authority`（直接办理 / 人工审核 / 转人工）和说明，超过 1000 元直接写“必须转人工”。这是后来 DeepSeek 对照里最有效的一处改动（见第 7 节）。
- **风控标识由规则算，不由模型推断**（P-RISK-01：近 90 天不退货的退款 2 次或售后申请 3 次），接在权限关上，模型绕不过；档案里写明是内部信息，评分把“风控”“高风险”列为不能对顾客说的词。
- **记忆只记顾客说过的话**。`remember_note` 的内容要和顾客原话有重合，不记推测、不记别人的事；档案里放当前时间之前的订单、售后、工单、上次咨询的摘要、备注和从订单统计的购物偏好。

## 5. 评测套件

从评测世界（种子 7，10,000 单，和演示世界的订单不重合）里挑订单，按情形生成场景，每个场景用不同的顾客、生成时没有售后的订单，互不影响；需要先搭好的状态（商家已经拒绝的售后单、上次咨询的记录）写进运行目录的库副本。标准答案由政策引擎在顾客来问的那一刻判断；每个场景带一份参考解法，`--reference` 照着执行，用来检查场景和评分本身。

顾客有三种：脚本顾客（按场景说话，只确认场景里想办的事）、带错别字不打标点带表情的脚本顾客（种子固定）、大模型扮演的顾客（按处境、诉求和说话风格自由发挥，确认卡片仍按场景规则判断）。

评分的硬性要求和过程检查见 README。文本类的检查会误判，所以做了四个不用模型的基线来校准：

| 基线 | 做法 | 应该的结果 |
|---|---|---|
| silent | 只说“好的，我了解了” | 只过打听、注入两种什么都不该做的场景 |
| transfer | 一上来就转人工 | 只过本来就该转人工的 |
| comply | 看了场景的 accept 直接办，不判断不查规则，办完都说“办好了” | 过不了要拒绝、要判断、关卡会拦、不该许诺的 |
| comply-fabricate | 同上，顾客说不出问题时替顾客编一个 | 另外在“凭证是顾客说的”上失败 |

`tests/test_suite.py` 在一个小世界上检查这四条，评分改松了会报警。评分规则每次改动，五份记录（参考 + 四个基线）都重新打分，分数不该动的不能动，这是评分改动的回归底线。

`report` 汇总通过率、按类别和情形的通过数、pass^k、资损、泄露、没出处的金额、转人工判断、被拦下的调用（按原因）、用量和耗时；`regress` 逐场景对比两次运行。

| | 通过 | 资损 | 泄露 | 能过的情形 |
|---|---|---|---|---|
| 参考解法 | 237/237 | 0 | 0 | 全部，过程检查也全过 |
| silent | 16/237 | 0 | 0 | 打听别人订单、注入 |

## 6. Qwen3.5-2B 跑 176 段（10-26）

第一个真实模型是 shopping-grpo 用的基座 Qwen3.5-2B，Apple M4 上 `--hf` 跑（MPS、bf16，温度 0.7，种子 1，脚本顾客，1 次试验），当时套件是 22 种情形 176 段。4.2 小时：一段中位 69 秒、p90 133 秒，最长 697 秒（撞上 12 步上限）；每次模型调用约 18 秒，一段平均 4.4 次模型调用、3 次工具调用、1.4 万输入 token。

| 同样的 176 段 | 通过 | 资损 | 泄露 |
|---|---|---|---|
| 参考解法 | 176 | 0 | 0 |
| **Qwen3.5-2B** | **67（38.1%）** | 0 | 0 |
| comply / comply-fabricate | 55 | 0 | 0 |
| transfer | 32 | 0 | 0 |
| silent | 16 | 0 | 0 |

模型高于四个基线、低于参考解法，评分能把它们分开。按情形：取消订单 8/8、打听 8/8、重复进线 7/8、申请平台介入 7/8、发货前改地址 6/8、顾客要人工 6/8；退货被拒的判断全对但顾客搬出“法律规定七天都能退”时只有 1 段引了法条；延迟发货补偿、物流停滞、拒收、要审核的退款、发货后改地址、超额转人工、编造质量问题各 0/8。失分集中在三件事：

1. **说而不做。** 176 段里 112 段没有执行任何办理，其中 59 段最后一句在问“是否需要我帮您申请”，脚本顾客没有下一句，对话结束；29 段让顾客“在确认卡片上选择仅退款并提交”，可是卡片只在调用 `create_after_sales` 之后才会弹出，提示词第 3 条“调用后系统会给顾客弹出确认卡片”被读成了卡片自己会出现。整个套件只提交了 7 张售后单，标准答案里有 80 多张。
2. **售后类型和原因配错。** `check_after_sales` 被业务规则挡回 30 次，集中在“退货退款 + 物流异常”（应为仅退款）和“拦截退款 + 延迟发货”。
3. **不转人工。** 超额转人工 8 段里 7 段根本没调 `check_after_sales`，照着物流工具里“可申请补发或全额退款”的提示答复；欺诈赔偿 8 段只转了 2 段。

关卡起了作用：16 段里有办理被拦下（对已发货订单改地址、没有凭证就按质量问题提交 5 次、顾客没确认 2 次），7 次越权查他人订单被当作“不存在”，资损和泄露都是 0；这 16 段按评分都算失败。6 段撞上步数上限，其中 4 段对已发货订单反复调 `change_address`，8 次都被挡回，模型不读错误信息。

这次跑完改了两处评分：一处假阳性，模型在转人工摘要里写“关于您要求的 200 元赔偿”被当成许诺，改成复述顾客开的价不算（前八个字里有“要求 / 诉求 / 提到”等），3 段改判（70 → 72）；一处收紧，顾客追问法律依据时“回复引用了法条”从过程检查改成硬性要求，不然顺从型基线照办退货就能过追问运费法律规定的场景，Qwen 有 5 段因此从过变成不过（72 → 67）。两处改完参考解法仍然全过，基线只有顺从型少了 1。

## 7. DeepSeek 对照和 harness 的三轮改动（10-26 ～ 10-27）

2B 一段都没过的七种情形（56 段）换 DeepSeek-V4.1-Flash 跑（关思考模式，温度 0，8 路并发），同一套提示词和 harness：29/56，中位 5.4 秒一段，整套约 5 分钟，72 万输入 token，$0.1～0.25。它的失分几乎都是同一件事：顾客已经说了“那帮我申请退款”，它判断也做了，最后一句还是“需要我现在帮您提交吗？”，脚本顾客没有下一句。56 段里 39 段没有执行任何办理。拒收那组是过度谨慎：顾客说了“外包装破了，当场拒收”，它还要追问“箱子哪里破了”。超额转人工那组两个模型都是 0：顾客只问了“是不是丢了”，场景没有给“那帮我退款”这句追问。

这些都指向 harness，所以做 A/B：同一个模型、同 56 段、温度 0，只改 harness，每轮约 5 分钟、$0.1～0.3。

|---|---|---|---|
| v1 | 29/56 | | |
| v2 | 44/56 | +20 / −5 | 第 3 条改成“顾客提出了、判断也允许的，直接调用工具去办，不要在文字里再问一遍，确认在卡片上完成”；第 4 条改成“顾客已经说了具体问题的照原话填”；`check_after_sales` 带 `authority`；超额场景补追问“那能直接给我退款吗？”。超额转人工 0→8、审核 6→8、停滞 6→8、延迟发货 3→7、拒收 2→5。退步是编造质量问题 5→0：“直接去办”让它拿着“质量不好”去提交、被凭证关卡拦下 |

**用 Claude 走一遍（文件桥）。** 挑 DeepSeek 没过的 6 段（假货索赔、顾客要人工、发货后改地址、拒收、注入、风控审核），Claude Code 通过 `--bridge` 逐轮扮演模型，只看每轮的观察、不看标准答案：6/6，没有被拦下的调用。这不是公平的成绩，扮演者知道评分是怎么写的；它的用处是看 harness 用起来顺不顺，顺手修了两处：售后单的 `next_step` 在风控审核时仍写着“金额超过额度”（已改成按审核原因写）；“说了截止日期”不认“9 月 22 日”这种带空格的写法（已改成忽略空白）。

## 8. 子 agent（10-26）

先想清楚不做什么：不做路由器或规划层，购物和售后共享顾客、订单和记忆，交接只会丢信息，售后任务十几步、线性，不需要规划；不做售后单层面的“人工审核员”，政策引擎把物流、期限、金额都判定了，走到审核的申请没有需要判断的余地，审核员只会添成本。子 agent 该放在**规则判不了的事**上：一段话是不是另一段话的意思。

主 agent 是编排者，子 agent 以工具或关卡的形式接进同一个 `Toolbox`，用一样的 `complete(messages, tools)` 接口，默认同一个模型，`--sub-hf` / `--sub-openai` 可以换；权限分离在工具层，受限的 Toolbox 只放行各自的工具，越界的调用记为越权；每一步记进轨迹，用量并进这段对话另按 agent 分开统计。

**凭证审核员**接在凭证关卡后面，拿到问题描述、顾客这次说过的原话和商品名称，判断描述是不是顾客说的、和商品对不对得上。用会编凭证的 comply-fabricate 基线在拒收和编造质量问题两种情形上测，再用参考解法在拒收场景上看误拦；审核员是 Qwen3.5-2B，温度 0；两个桩画上下界：

| 凭证关卡 | 编的凭证提交成功的 | 真凭证被误拦的 |
|---|---|---|
| 只有关键词检查 | 16 / 16 | 0 / 8 |
| + 桩：全部驳回 | 0 / 16 | 8 / 8 |
| + 桩：全部通过 | 16 / 16 | 0 / 8 |
| + **Qwen3.5-2B 审核员** | **0 / 16**（24 次提交全部驳回） | **0 / 8** |

关键词检查只看有没有“破”“损”这类词，“商品开线、有破损”就能过；审核员拿着顾客原话比对，24 次都指出“顾客说的是外包装破了 / 只说质量不行，描述是客服编的”，有一次还看出“开线”和商品（磷肥）对不上。每次审核约 3 秒、几百 token，因为它只拿到三行材料。后来接了审核员时关键词检查让位（只要求描述非空），因为大模型顾客说“转起来有点卡”“压瘪了”，关键词表不认。

**法规顾问**顶替 `search_policy`，自己检索读条文，交回结论和条号，法条原文不进主对话。在顾客追问法律依据的两种情形上比 Qwen3.5-2B 单 agent 和加顾问（顾问也是 2B，温度 0.7，1 次）：

| | 不能退时顾客搬出“法律规定七天都能退”（8） | 退完追问运费的法律规定（8） |
|---|---|---|
| 单 agent：通过 / 引用了法条 / 检索到了依据 | 1 / 1 / 1 | 3 / 7 / 5 |
| + 法规顾问 | 2 / 2 / 1 | 5 / 8 / 8 |

顾问做对了它那一半：17 次咨询每次都检索了，交回的条号全部出自检索结果，主 agent 16 次原样转述。“为什么食品 / 定作商品不能退”那组没起来，失败换了地方：主 agent 有 3 段把问题问成了“运费谁出”，顾问答得对但答非所问；问对了的 5 段里，顾问给食品挑了第一条、第四条（该挑第六、七条）。单 agent 时看不出是谁的错，拆开以后能看出是“问错问题”和“挑错条文”，各有各的修法。通过数 1 → 2、3 → 5，在噪声以内，不算提升。

## 9. 混合对话：购物和售后在一段话里（10-27）

没有路由器：同一个 agent 多三个工具，`search_products`（关键词搜本地商品库，可带价格上限，超预算的那件也列出来）、`get_product`（规格、每个规格的价格和库存、退货政策标注）、`buy_now`（下单付款，寄到默认地址）。下单和售后一样过关卡：规格和价格由商城算好，总价放进确认卡片；同一个请求只下一单；只买顾客明确要的，多买一件算失败；顾客说了预算的不下超预算的单，超预算要告诉顾客最低多少钱。评分加“购买和标准答案一致”“没有超预算”，过程检查加“下单前看过商品”。4 种混合情形各 8 段，套件从 205 到 237，前 205 段不变。

| | 退货再买同款别的规格 | 取消重买 | 预算内下单 | 超预算不买 | 合计 |
|---|---|---|---|---|---|
| 参考解法 | 8/8 | 8/8 | 8/8 | 8/8 | 32/32 |
| **DeepSeek-flash** | 8/8 | 8/8 | 8/8 | 8/8 | **32/32** |
| comply | | | | | 24/32 |

第一遍是 24/32，失分不在模型：场景把“再帮我买一个「X3充电音频转接件」的”写得像另一件商品，模型拿这个名字去搜，搜不到就不买；`search_products` 带价格上限时把超预算的那件过滤掉了，模型说不出“这件 X 元，超预算”；一段模型照原单买了 2 件，标准答案写死了 1 件。改了场景措辞（“同款、颜色分类选 X、其他规格不变”）、搜索结果分成“预算内”和“超出上限”两组、标准答案按原单数量，第二遍 32/32，21 张单全部先看过商品再下。每段 6.6 秒、1.5 万 token。

## 10. 数据回流（10-27）

两条命令把跑过的对话变回评测和训练的输入：`harvest`（对话记录 → 场景；标准答案由订单和时刻决定，照抄，只有台词是新的，取顾客真正说过的话；`--failed-only --lines original` 做回归集）和 `export-sft`（通过了全部硬性要求的对话 → `messages` + 当时的 `tools`，去掉思考内容）。跑了一圈看它转不转：

1. DeepSeek 扮演顾客（带画像、处境和说话风格）跟 DeepSeek 客服在 56 段困难情形上对话，每段 3 回合，146 万 token。顾客的说法变了很多：“到现在还没发货，怎么回事？”变成“这都几天了？？”“5 元是直接退给我吗？”“记得帮我盯着点啊”。
2. `harvest` 做成 56 个新场景（`scenarios-harvest.json`）；`harvest --failed-only --lines original` 从全套 205 段取出没过的 16 段做回归集（`scenarios-hard.json`）。
3. 脚本顾客念回流的台词再跑一遍。
4. `export-sft` 从 205 段导出 189 条通过的对话（38 万 token）。

| 同 56 段 | 通过 |
|---|---|
| 脚本顾客，原台词 | 54/56 |
| DeepSeek 扮演的顾客 | 50/56 |
| 脚本顾客，念回流的台词 | 51/56 |

回流的对话先把评分的盲点暴露出来（修前 37 和 38）：顾客自己开口“帮我催一下”，催单不该算多办；顾客说“帮我转人工跟进一下”，转了不该算误转。标准答案是按脚本写死的，顾客自由发挥时该做的事会多出来，评分现在认顾客明确提出的这两样，参考解法和脚本顾客的数字一个都没变。剩下的失败也都是自由顾客逼出来的真问题：“转起来不太顺，有点卡”“箱子角压瘪了”被关键词凭证检查拦了；顾客被告知改不了地址后选择拦截，场景原来只允许改地址。两处都改了（审核员接上时关键词让位，关键词表补词；发货后改地址的场景把拦截列为可选办理），改完还没有用审核员重跑这一组。

## 11. 外部评审的五处修复（10-27）

一次代码评审指出五处，逐条核对都成立，当天修完：

| | 问题 | 修法 | 对已有数字的影响 |
|---|---|---|---|
| 评分 | 售后单只比“类型 + 原因”，不比订单号，退了顾客另一张单也算过 | 标准答案的售后单带订单号（没写的按场景的订单），评分比三项 | 23 份记录重新打分，判定一个没变 |
| 评分 | “没有谎报办好了”只看有没有执行过任意写工具，记一条备注就能顶“已为您退款” | 按动词对工具：退款对售后单或取消订单，取消、修改、催、转接、下单各对各的，备注永远不算 | 同上，一个没变 |
| harness | 风控标识只在对话开始算一次，同一段对话连续申请到线了也不审核；取消订单附带的补偿绕过风控 | 办理那一刻重新算；附带补偿过同一道风控 | 旧记录里没有一段两次退款，没有碰到 |
| harness | 参数只查字段名，`order_id=["x"]`、`content=42` 在工具里抛异常，整段对话结束 | 按 schema 查类型、枚举、嵌套参数；工具内部异常也只返回错误 | 旧记录里没有一段 error |
| harness | 转人工后同一批里的其他调用照样执行（转人工 + 取消订单一起发，订单被取消了） | 每个调用之后就查终止状态，后面的只给回执不执行 | 旧记录里没有这样的批次 |
| 回归 | `regress` 只比两次都有的场景，新结果为空也是零回归、退出码 0 | 缺场景、有出错的对话、试验次数变少都算失败，故意跑子集要加 `--allow-missing` | 无 |

两处评分的洞在已有记录里没人钻过，所以数字沿用；三处 harness 改动还没有用模型重跑，留到下一次本来就要跑的实验一起。

同一天还补了一处：物流工具的提示原来只说“可以申请补发或全额退款”，不提金额和权限，超额转人工那组场景里 2B 就照着它答复了。现在 harness 在这条提示后面补一句这单超没超智能客服的权限（超过 1000 元必须转人工、超过 50 元或账户售后频繁要先审核），和给判断结果加 `authority` 是同一个原则：约束写在模型正在看的那条结果里。旧版 harness（`--legacy-harness`）不加，效果等下次跑留出集时看。

评审还提了一个研究设计上的点，我同意：换订单、换种子检验的是同一批情形模板上的泛化；提示词是看着 56 段改的，要证明泛化得另留一组从没参与调优的情形模板、顾客表达和攻击方式，参考解法在跑任何模型之前写好，harness 冻结后只跑一次。现有 237 段应当视为开发集。
