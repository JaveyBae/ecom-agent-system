# 法规与平台规则知识库

售后 Agent 用来检索依据的知识库，共 2,590 条，分两部分：

- **法规**：27 部现行有效的法律、行政法规、司法解释、部门规章和规范性文件，按“条”切分，2,550 条（含 8 个附件）
- **平台规则**：虚构平台“ShopSim 模拟商城”的 40 条规则，自己拟定，每条标注了它依据的法规条文

支持 BM25、向量和混合检索，可以按层级过滤。另有一份评测用的最高法典型案例集（31 个），不进知识库，见文末。

法律法规和国家机关的规范性文件不受著作权保护（《著作权法》第五条），可以原文收录。

**来源的选择**：优先用国家法律法规数据库、中国政府网和发文部门的网站。市场监管总局官网从当前网络访问被拒（403），所以部分规章用了商务部全球法规网或北京市市场监督管理局法规栏目里的全文。

**有效性**：国家法律法规数据库里的文件只取状态为“有效”的最新版本。部门规章和规范性文件没有可查询的接口，版本根据来源页面上的修订记录人工确认，记录在 `crawl_rules.py` 里；移动电话机和家用视听三包规定的现行有效性没有经过数据库核验，条目里有 `status_note` 说明。

**清洗**：
- 三包规定的附件（实施三包的商品目录、性能故障表等）拆成了单独的条目，表格框线换成了空格；来源页面只有标题、没有内容的附件不收录
- 全角数字和字母转成了半角（“２００１年”→“2001年”），中文标点不变
- 去掉了来源网站附加的免责声明

**暂未收录**：
- 微型计算机商品修理更换退货责任规定（三包）：只找到地方市场监管局网站（从当前网络访问超时）和第三方转载，没有核对过的官方文本
- 《快递服务》国家标准（GB/T 27917）：标准文本受著作权保护，不收录

## 平台规则

真实平台的规则（淘宝、京东等）受著作权保护，平台协议一般也禁止抓取；而且系统里的平台本来就是虚构的。所以平台规则是参照常见行业做法自己拟定的，写在 `platform_rules.yaml`，共 7 类 40 条：七天无理由退货、质量问题、发货与物流、价格与优惠、会员、特殊品类、客服与纠纷（含 P-RISK-01 售后频繁账户的人工审核）。

`platform_rules.yaml` 是平台规则的唯一来源：
- 规则文本由模板和参数渲染，例如 `{ship_hours}` 小时内发货，改数值只改参数
- 同一份参数将来也给 harness 的代码检查和任务生成器计算标准答案用，三处不会不一致
- `build_platform_rules.py` 会检查：占位符和参数一一对应；`legal_basis` 里的条文在法规知识库里存在；文本里引用的其他规则编号（如“见 P-MEM-01”）存在

拟定时遵守的原则：平台规则可以比法律对消费者更有利，不能更不利。例如退款时限定为 3 日（法定上限 7 日）；“仅退款”只用于未发货、运输中丢失或损毁等情形，因为《网络交易平台规则监督管理办法》第二十七条禁止平台强制商家仅退款不退货；智能客服在用户要求时必须转人工，依据同一办法第十九条。

文件里标了“待定”的数值是设计选择，不是法律要求。

## 用法

```bash
uv run python knowledge/crawl_flk.py            # 抓取国家法律法规数据库 → processed/laws.jsonl
uv run python knowledge/crawl_rules.py          # 抓取部门规章 → processed/rules.jsonl
uv run python knowledge/build_platform_rules.py # 校验平台规则 → processed/platform_rules.jsonl
uv run ecom-kb build                            # 向量化，生成 index/（首次运行会下载约 1.2GB 的模型）

uv run ecom-kb search "耳机拆封试了一下，还能七天无理由退货吗" -k 3
uv run ecom-kb search "快递在路上丢了，商家让我自己去找快递公司" --level 平台规则
uv run python knowledge/eval_retrieval.py       # 在标注查询上比较三种检索方式
uv run python knowledge/tune_fusion.py          # 扫描融合权重，比较有无同义词扩展
uv run ecom-kb serve                            # 检索台网页，见下文
```

抓取脚本每次请求间隔 1.5 秒，已下载的文件缓存在 `raw/`，重复运行不会重新下载。每部法规切分后都会检查条号是否从 1 连续递增，不连续时会在输出里报出来。

## 数据格式

`processed/*.jsonl` 每行一条：

```json
{"chunk_id": "2c909fdd...#第二十五条", "title": "中华人民共和国消费者权益保护法",
 "level": "法律", "article_no": "第二十五条", "chapter": "第三章 经营者的义务",
 "text": "经营者采用网络、电视、电话、邮购等方式销售商品，……",
 "issuer": "全国人民代表大会常务委员会", "promulgated": "2013-10-25", "effective": "2014-03-15",
 "status": "有效", "source": "国家法律法规数据库 flk.npc.gov.cn", "source_file": "https://..."}
```

平台规则的 `level` 是“平台规则”，`article_no` 是规则编号（如 `P-SHIP-06`），另有 `legal_basis`（依据的法规条文）和 `params`（参数）。

`index/` 可以随时重新生成：`embeddings.npy` 是归一化后的向量矩阵，`chunks.jsonl` 是同序的元数据，`manifest.json` 记录模型名和语料哈希。

## 检索方式

- **BM25**：jieba 分词，适合“拆封”“赠品”这类关键词。查询会按 `synonyms.yaml` 把口语说法扩展成法规用语，扩展词降权（见下文“同义词扩展和融合权重”）
- **向量**：Qwen3-Embedding-0.6B，查询侧加检索指令。每条向量化前会加上文件名、章节和条号，因为同一句“七日内退货”出处不同，含义也不同
- **混合**：两路各取前 50 名，用加权 RRF（k=60）融合：第 r 名得 权重 / (60 + r)，默认两路等权
- 可以按层级（`--level`）或文件名先过滤，再检索

## 检索台

```bash
uv run ecom-kb serve              # 打开 http://127.0.0.1:8000，--port 换端口
```

本地网页，用来看检索是怎么排出来的，后端是 FastAPI（`src/ecom_agent_system/server.py`），前端是不需要构建的静态页面（`static/`）：

- 同一个问题的 BM25 前 10、向量前 10 和融合结果并排显示。每条标出它在两路里的名次和融合后的名次，鼠标移到一条上，三栏里的同一条会一起高亮
- 显示 BM25 的查询词和触发了哪些同义词；正文里黄色是问题里的词，绿色是扩展出的法规用语
- 可以拖动向量权重（0 是只用 BM25，1 是只用向量）、开关同义词扩展、按层级过滤。两路名次按（查询、层级、是否扩展）缓存，拖动滑块只重新融合
- 平台规则下的“依据”可以点开，看它引用的法条原文
- 检索设置写在地址栏里，复制链接就能复现同一个结果

接口：`GET /api/search?q=…&dense_weight=0.5&expand=true&level=法律`、`GET /api/article?citation=《…》第X条`、`GET /api/info`，参数校验和返回结构有测试（`tests/test_server.py`）。

## 冒烟测试结果

`eval/` 下有两组口语化问题：`smoke_queries.jsonl` 17 条，答案在法规里；`smoke_platform_queries.jsonl` 12 条，答案在平台规则里。每条标注了一个或多个能回答它的条目，命中任意一个即算召回。

| 查询 | 检索范围 | 方式 | R@1 | R@5 | R@10 | MRR@10 |
|---|---|---|---|---|---|---|
| 法规 17 条 | 只检索法规 | BM25 | 0.35 | 0.47 | 0.59 | 0.408 |
| | | 向量 | 0.41 | **0.82** | **0.94** | 0.589 |
| | | 混合 | **0.53** | 0.76 | 0.82 | **0.629** |
| 法规 17 条 | 全部层级 | 混合 | 0.35 | 0.65 | 0.76 | 0.503 |
| 平台 12 条 | 只检索平台规则 | 混合 | 1.00 | 1.00 | 1.00 | 1.000 |
| 平台 12 条 | 全部层级 | BM25 | 0.92 | 0.92 | 0.92 | 0.917 |
| | | 向量 | 0.33 | 0.75 | 0.83 | 0.505 |
| | | 混合 | 0.83 | 0.92 | 0.92 | 0.854 |

BM25 和混合是加了同义词扩展之后的结果，加之前的对比见下一节。会员等级改成与 ShopSimulator 用户画像一致（普通、黄金、铂金、钻石）后，P-MEM-01 的文本变了，平台查询在全部层级里单用向量的 R@1 从 0.50 降到 0.42（1 条查询的名次变化），其余结果不变。

2026-10-25 平台规则从 35 条加到 39 条（P-QA-05 质量问题的凭证、P-SHIP-11 修改收货地址、P-SHIP-12 催发货和催派送、P-SVC-06 商家拒绝售后申请），并改了 P-SHIP-05、P-SVC-04 的文本，重建索引后重跑：法规查询只检索法规时，混合检索 R@5 从 0.71 升到 0.76（1 条查询进了前 5，BM25 的词频统计包括平台规则，加条目会改变法规的分数）；平台查询在全部层级里单用向量的 R@1 从 0.42 降到 0.33（又一条查询被新规则挤下第 1 名）。其余结果不变。

2026-10-26 加 P-RISK-01（售后频繁账户的人工审核）后重建索引（2,590 条），冒烟评测的四组配置和检索决策评测全部重跑，数字和上面的表完全一样。

样本太少，一条查询就相差 0.06 到 0.08，**不能据此下结论**。平台规则的查询和规则文本都是我写的，命中率高不说明问题。目前能看到的现象：
- 口语问题和法条用词差别大，BM25 在法规上召回很低；等权 RRF 提高了第一名的命中率，但前 5 名召回不如单用向量
- 平台规则和法规混在一起检索时会互相挤占：平台规则用词口语化，把法条挤下去；向量检索又常把法条排在平台规则前面
- 典型的失败是问题表面和真正的法律依据不一致。例如“快递丢了，商家让我自己找快递公司”，只检索法规时前 10 名都是快递赔偿规则，答案《电子商务法》第二十条没进前 10；但平台规则 P-SHIP-06 能直接命中，它的 `legal_basis` 指向的正是第二十条

所以 Agent 的检索工具更适合分层检索：先查平台规则，再沿 `legal_basis` 取对应法条，同时单独查一次法规，而不是把所有条目混在一起排序。

q17 的标注在第一次看到结果后补充了《消费者权益保护法》第二十九条（个人信息保密），这是标注遗漏，补充前后的指标几乎没有变化。

## 同义词扩展和融合权重

顾客说“七天”“快递柜”“假货”，法条写“七日”“智能快件箱”“假冒”，这是 BM25 在法规上召回低的主要原因。`synonyms.yaml` 收了 121 条口语说法到法规用语的映射，只扩展 BM25 的查询：文档不改，向量检索的查询也不扩展，因为向量模型本身能理解近义说法。表里右边的词都必须在语料里出现过，`tests/test_synonyms.py` 会检查。

这张表按电商售后的常见说法整理，没有对着评测题逐条补词。冒烟查询里，17 条法规问题有 12 条、12 条平台问题有 6 条会触发扩展。

**扩展词要降权。** 扩展词和原词同权时，单用 BM25 变好了，混合检索反而变差。例如 q07 的“假货”扩展出“假冒”“以假充真”，把行政处罚条文排了上来，而标注的是民事赔偿条文，相关条文从第 1 名掉到第 15 名；q13 的“店铺”扩展出“平台内经营者”，这个词出现在 54 条里，把整部电子商务法都拉了进来。现在扩展词单独打分，乘以 0.3 再加到原查询的得分上（`EXPANSION_WEIGHT`，0.2 和 0.3 效果相近）：

| 等权混合检索，R@5 / MRR@10 | 法规·只查法规 | 法规·全部层级 | 平台·全部层级 |
|---|---|---|---|
| 不扩展 | 0.65 / 0.606 | 0.65 / 0.468 | 0.92 / **0.875** |
| 扩展词同权 | 0.59 / 0.518 | 0.65 / 0.452 | 0.83 / 0.847 |
| 扩展词 × 0.3（现在） | **0.71 / 0.627** | 0.65 / **0.503** | 0.92 / 0.854 |

平台·只查平台规则三种都是 1.00，没有列出。扩展词的权重是在冒烟查询上选的；最高法案例没有参与选择，加扩展后混合检索的命中@10 从 0.37 到 0.42，覆盖@10 从 0.33 到 0.37，多找到 1 个案例。单用 BM25 在案例上没有变化，因为基本案情是法院写的，口语说法少。

**融合权重还没定。** `tune_fusion.py` 在冒烟查询上扫描向量权重 w（BM25 权重为 1 − w），对四种查询集与检索范围的组合取平均：

- 平均 R@5 最高的是 w = 1，也就是只用向量（0.85），但只比混合多对 1 题
- 平均 MRR@10 最高的是 w = 0.4（0.751），只用向量是 0.679：混合检索更容易把相关条文排在前面
- 最高法案例上，只用向量的命中@20 是 0.63，等权混合是 0.47

一题就差 0.06，这些差别不足以定下权重，默认值暂时保持等权。要定权重，需要先扩充评测集：把典型案例改写成顾客问题，并做分级相关性标注。

### 在典型案例上的检索召回

`uv run python knowledge/eval_court_retrieval.py`：19 个有可对应引用的案例，只用“基本案情”作查询，相关条文取法院引用的条文（共 30 条，其中 7 条在核心包里），只在法规里检索。

| 方式 | 命中@5 | 命中@10 | 命中@20 | 覆盖@10 |
|---|---|---|---|---|
| BM25 | 0.21 | 0.26 | 0.32 | 0.27 |
| 向量 | 0.37 | 0.42 | 0.63 | 0.33 |
| 混合 | 0.32 | 0.42 | 0.47 | 0.37 |
| 分层（平台规则的依据 + 混合） | 0.32 | 0.42 | 0.47 | 0.33 |

命中@k：前 k 条里至少有一条法院引用的条文；覆盖@k：法院引用的条文里有多少比例出现在前 k 条。

表中是加了同义词扩展之后的结果；加之前混合检索的命中@10 是 0.37，覆盖@10 是 0.33。下面几条分析是在加同义词扩展之前做的。

- **比冒烟测试差很多**：真实纠纷的前 10 名命中率只有约 0.4，长尾条文前 10 名只覆盖 6/23（混合检索）
- **法规找得到，条文找不准**：前 10 名里有法院所引法规的案例占 17/19（0.89），有所引条文的只占 7/19（0.37）
- **不是用户说法的问题**：改用法律化表述的“要旨”作查询，命中@10 也只有 0.42～0.53
- **两个改进没有效果**：沿条文里的交叉引用展开一层，命中@10 仍为 0.37（全库只有 42 条法条引用了其他条文）；先选法规再检索条文，命中@10 最多到 0.42，只多一个案例，在误差范围内
- **指标偏严**：法院只引用它用到的条文，检索出的其他法规里含义相同的条文不算命中。例如过度收集个人信息的案例，检索到了《民法典》第一千零三十五条（处理个人信息的原则），但法院引用的是《个人信息保护法》第十五、十六条。要得到可信的召回率，需要对检索结果做分级相关性标注

样本只有 19 个，一个案例就相差 0.05。

## 检索决策评测集

`eval/retrieval_decision.jsonl`，43 道顾客口吻的问题，用来考售后 agent 三件事：该不该检索、检索词写得好不好、答案对不对。

| 题型 | 题数 | 该不该检索 | 来源 |
|---|---:|---|---|
| 法规 | 18 | 必须 | 最高法典型案例改写，只用基本案情，不透露判决 |
| 法规（短问题） | 7 | 必须 | 同一批案例压成一句话，信息少，答案往往要带条件 |
| 平台规则 | 7 | 必须 | 只有平台规则里有答案，比如铂金会员的退货期 |
| 订单工具 | 6 | 不需要 | 答案在顾客的订单数据里，要调 `list_orders`、`track_shipment` 等 |
| 闲聊 | 3 | 不需要 | 不需要任何工具 |
| 超出范围 | 2 | 不需要或可选 | 选购咨询、非平台的预付卡纠纷，不应调用订单工具 |

每道题标了：

- `retrieval`：required、optional 或 unnecessary；
- `scope`：应检索的范围；
- `expected_tools`：除检索外应该调用的工具；
- `expected_citations`：命中其中任意一条就算检索到了；
- `court_citations`：其中法院自己引用的条文，其余是我按判决理由补标的同义条文。法院没写条号的 2 题全部是补标，第 18 题不标条文、只评结论；
- `answer`：结论和必须讲到的要点，用来判答案正确性。

`tests/test_retrieval_decision.py` 检查标签合法、条文都在语料里、来源案例都存在。题目是我写的，标注只经过我自己检查。

### 直接拿原话检索的基线

`uv run python knowledge/eval_retrieval_decision.py`：不经过 agent，直接用顾客原话在标注的范围里检索，看标注的条文排第几。

| 题型 | 方式 | 题数 | 命中@1 | 命中@5 | 命中@10 | 命中@20 |
|---|---|---:|---:|---:|---:|---:|
| 法规 | BM25 | 17 | 0.12 | 0.24 | 0.35 | 0.35 |
| | 向量 | 17 | 0.29 | 0.41 | 0.47 | 0.53 |
| | 混合 | 17 | 0.24 | 0.41 | 0.47 | 0.53 |
| 法规（短问题） | BM25 | 7 | 0.14 | 0.14 | 0.29 | 0.43 |
| | 向量 | 7 | 0.29 | 0.43 | 0.57 | 0.86 |
| | 混合 | 7 | 0.14 | 0.43 | 0.43 | 0.57 |

- **法规题比冒烟测试难得多**：混合检索前 5 名只命中四成。抽查没命中的题，排第 1 的大多确实不相关，不是标注太严。
- **失败的原因是检索器被表面词带偏**：顾客讲的是事实，真正的法律问题是格式条款怎么解释、孩子的民事行为能力、客服算不算代表店铺，这些词问题里都没有。“直播”带出了直播营销平台的责任条款，“退票”带出了客运合同的退票条款。
- **所以要评 agent 写的检索词**：先把顾客的话改写成法律问题再检索，应该能明显提高命中。同一批题，比较“原话检索”和“agent 改写后检索”的命中率，就能衡量改写的作用。
- 平台规则题几乎都能找到，因为问题和规则用词接近。表中是平台规则加到 39 条之后的结果（加到 40 条后重跑，不变）；加之前平台规则题的命中@1 是 BM25 0.57、向量 0.86、混合 0.57，法规题不变。

### 接上模型后评什么

- **检索决策**：
  - required 的题有没有检索，漏检的比例；
  - unnecessary 的题有没有白白检索，多检的比例；
  - 订单工具题有没有调对工具。
- **检索质量**：agent 实际检索到的结果里，有没有标注的条文。
- **答案**：分开报结论准确率、要点覆盖率，以及严重错误率（结论错了，或者承诺了规则里没有的东西）。短问题的答案应该带条件，武断地下结论算错。
